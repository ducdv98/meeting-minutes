# Windows app feasibility: shell, distribution, and subscriptions

Researched 12 October 2026. This feasibility assessment evaluates porting a supplied macOS app architecture to Windows; it is not a Store certification decision. The platform conclusions below come from first-party documentation.

## Verdict and recommended path

**Feasible.** Keep the existing Expo web/React/TypeScript UI in **Electron**, replace the Swift capture host with a Windows native helper for microphone and system audio, and ship first as a **signed, per-user NSIS installer** with `electron-updater`. Use the existing account/Convex identity to grant subscriptions purchased through **RevenueCat Web Billing with Stripe** (or an existing Stripe/Paddle catalog connected to RevenueCat). This preserves the most code and gives a straightforward path to launching the user's installed coding CLI. Electron supports native addons, child processes, and tray UI; Expo exports a web bundle; electron-builder supports NSIS updates; RevenueCat's Web SDK supports web purchases and shared entitlements. [Electron native code](https://www.electronjs.org/docs/latest/tutorial/native-code-and-electron), [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Expo web export](https://docs.expo.dev/deploy/web/), [electron-updater](https://www.electron.build/docs/features/auto-update/), [RevenueCat Web](https://www.revenuecat.com/docs/web/payment-integrations).

After testing CLI reuse and capture on real Windows machines, submit the **same signed offline EXE** as an unpackaged Win32 Microsoft Store listing if discoverability matters. This route retains the app's own installer, update mechanism, and third-party billing; Microsoft does not update existing MSI/EXE installations. An MSIX Store build is a later, separate channel if Store-managed install/update and free Store signing outweigh extra packaging and certification work. [Microsoft Win32 distribution comparison](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store), [MSI/EXE update behavior](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/publish-update-to-your-app-on-store).

## Shell choices

“Size” below is a relative architectural comparison, **not a measured installer size**. A capture helper and bundled model/runtime assets may dominate any shell difference. Electron ships Chromium and Node; Tauri uses the installed WebView2 runtime unless the installer bundles it. [Electron security architecture](https://www.electronjs.org/docs/latest/tutorial/security), [Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/), [Tauri Windows installer options](https://v2.tauri.app/distribute/windows-installer/).

| Shell | UI reuse and size | Native capture, tray/background, updates | Assessment |
| --- | --- | --- | --- |
| **Electron** | Direct reuse of Expo web output and existing Electron/Node main-process code; largest baseline because Chromium and Node ship with it. [Expo export](https://docs.expo.dev/deploy/web/), [Electron architecture](https://www.electronjs.org/docs/latest/tutorial/security) | Windows native addon/DLL or child helper can expose WASAPI; built-in `Tray`; app can stay running after a window closes; built-in `autoUpdater` supports Squirrel.Windows and current Electron MSIX packaging, while `electron-updater` supports NSIS. [Native addons](https://www.electronjs.org/docs/latest/tutorial/native-code-and-electron), [Tray](https://www.electronjs.org/docs/latest/api/tray/), [process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Electron updater](https://www.electronjs.org/docs/latest/api/auto-updater/), [electron-builder updater](https://www.electron.build/docs/features/auto-update/) | **Best first Windows port.** Keep native capture behind a narrow IPC boundary. |
| **Tauri v2** | Can load the same web UI; uses WebView2 rather than bundling Chromium, normally a smaller shell, but a Rust command/sidecar layer replaces Node main-process code. Offline WebView2 bundling adds about 127 MB according to Tauri. [WebView](https://v2.tauri.app/reference/webview-versions/), [installer](https://v2.tauri.app/distribute/windows-installer/) | Rust can call native APIs; shell plugin can launch processes but requires explicit command/argument permissions from web content; tray and signed updater plugins exist; Windows MSI and NSIS targets exist. [Shell](https://v2.tauri.app/plugin/shell/), [Tray](https://v2.tauri.app/reference/javascript/api/namespacetray/), [Updater](https://v2.tauri.app/plugin/updater/), [installer](https://v2.tauri.app/distribute/windows-installer/) | Good later optimization if measured Electron cost warrants a main-process rewrite. |
| **.NET: WinUI 3, WPF, Avalonia** | WinUI/WPF use XAML and Avalonia uses its own XAML-style UI, so a native UI means rewriting React screens. WinUI 3 or WPF can instead host the web export in WebView2; Avalonia also documents a NativeWebView. [WinUI WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/get-started/winui), [Avalonia web content](https://docs.avaloniaui.net/docs/app-development/embedding-web-content) | C# can use Windows APIs or call a native helper; Avalonia has a first-party tray control, whereas WinUI 3 lacks a first-party tray control and needs Win32/library integration. MSIX Store or direct distribution is possible; direct updates must be built/configured separately. [Avalonia tray](https://docs.avaloniaui.net/docs/platform-specific-guides/windows), [WinUI tray gap](https://learn.microsoft.com/en-us/windows/apps/get-started/line-of-business/migrate-winforms-patterns), [Windows distribution options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/publish-first-app) | Sensible for a Windows-native product, but a worse fit for this existing Electron UI/daemon architecture. |
| **Flutter** | Flutter draws a Dart UI, requiring a screen rewrite and new state/data bindings; a Windows build includes its engine and runtime assets, so it is not comparable to a tiny WebView wrapper. [Flutter desktop](https://docs.flutter.dev/platform-integration/desktop), [Windows bundle contents](https://docs.flutter.dev/platform-integration/windows/building) | Windows runner is C++; Dart FFI or a Windows plugin can call WASAPI/native code. Tray and updater need plugins or runner code. Flutter documents Store MSIX and direct Windows distribution but no built-in Electron-style updater in its Windows distribution guide. [Flutter Windows build/interop/distribution](https://docs.flutter.dev/platform-integration/windows/building) | Lowest reuse; choose only for an intentional UI rewrite. |

For capture, Windows [WASAPI loopback](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording) can capture output audio, and the [WASAPI capture interfaces](https://learn.microsoft.com/en-us/windows/win32/coreaudio/wasapi) handle microphone endpoints. A Windows helper is required regardless of the chosen shell because the supplied macOS Swift capture host cannot run on Windows. Loopback captures an output mix, and protected streams may be excluded; test device changes, headphones, simultaneous mic/system streams, and protected audio rather than assuming macOS capture behavior transfers. [Microsoft loopback documentation](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording).

As of 12 October 2026, [Store policy version 7.19](https://learn.microsoft.com/en-us/windows/apps/publish/store-policy-archive/store-policy-7-19) is effective. [Version 7.20](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies) was published 15 September but takes effect 22 October 2026; check the policy effective at submission time. In particular, the current policy requires an accurate privacy policy for Win32/Desktop Bridge products, legitimate capability declarations, and consent for certain sharing of personal information; it does not state a blanket ban on a recording app or on launching an installed CLI. A visible recording state, clear user initiation, and explicit disclosure of any cloud transcription or sharing are prudent product requirements. Check applicable recording-consent law separately. ## Can a Windows desktop app launch the user's existing Codex or Claude Code?

**On ordinary Windows, technically yes, with conditions.** A full-trust (`mediumIL`) MSIX desktop process has standard desktop-app permissions, although MSIX virtualizes some file/registry state; an unpackaged EXE has normal desktop process access. Electron's main process can start a child process, and Tauri's shell plugin can do so with scoped permissions. This supports discovery of a Windows-installed executable and launching it under the signed-in user. `runFullTrust` grants the packaged desktop trust level; it does **not** itself guarantee a particular CLI, login, or Store certification outcome. [MSIX trust model](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview), [capabilities](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations), [Electron child processes](https://www.electronjs.org/docs/latest/tutorial/process-model), [Tauri shell](https://v2.tauri.app/plugin/shell/).

The app should locate the executable in the **user's own** `PATH` (plus an explicit configured path), launch it with an argument array from the trusted main/helper process, and leave its credential files to the CLI. Codex's official authentication documentation says CLI login is cached in `~/.codex/auth.json` or the OS credential store and reused by the CLI; this implies reuse when the launched process has the same Windows user/profile and `CODEX_HOME` configuration. Claude Code documents Windows native/Git Bash and WSL installations, login methods, and noninteractive `claude -p`; its credential reuse likewise depends on invoking the same installation/user environment. Avoid copying tokens into the app or logging CLI environment/output that contains secrets. [Codex authentication](https://learn.chatgpt.com/docs/auth), [Claude Code setup](https://code.claude.com/docs/en/setup), [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference).

**WSL is a separate target.** Windows can use `wsl.exe -d <distro> -- <command>` to invoke a Linux-installed CLI, but WSL and a Windows npm/global install have distinct `PATH`, home directory, and credential store. Detect WSL and a registered distro; let the user select the distro and verify its own `codex`/`claude` login. This is an inference from Microsoft's WSL process/environment documentation and the CLIs' own authentication models, not a promise that a Windows login automatically authenticates WSL. [WSL interoperability](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop), [Codex authentication](https://learn.chatgpt.com/docs/auth), [Claude Code setup](https://code.claude.com/docs/en/setup).

**Store and S mode caveat.** Microsoft's Desktop Bridge certification tests for Windows S mode flag attempts to launch executables outside the package; non-gaming Store policy also limits undisclosed dependencies and dynamic code changes. Accordingly, verify the actual Ask integration with a packaged MSIX and the Windows App Certification Kit, disclose optional Codex/Claude dependencies and purpose in metadata, and do not promise S mode support. This is a certification risk, not evidence that full-trust MSIX on ordinary Windows has the Mac App Sandbox prohibition. [Desktop Bridge tests](https://learn.microsoft.com/en-us/windows/uwp/debug-test-perf/windows-desktop-bridge-app-tests), [Store policies 10.2.2–10.2.4](https://learn.microsoft.com/en-us/windows/apps/publish/store-policy-archive/store-policy-7-19), [MSIX full trust](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview).

This differs from the reported Mac App Store blocker: Apple's [App Sandbox file-access rules](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) limit access to external files, and [child processes inherit the parent's sandbox](https://developer.apple.com/documentation/foundation/process). The Windows full-trust MSIX model documents standard desktop permissions, subject to the S mode and certification caveats above. [Microsoft MSIX trust model](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview).

## Subscriptions and licensing

Microsoft Store subscription add-ons use `Windows.Services.Store`/`StoreContext` and Store-managed recurring billing. Microsoft's subscription guide covers UWP and notes extra `StoreContext` setup for Desktop Bridge; a packaged desktop build should prototype this before committing to it. Microsoft states its commerce fee is **15% for apps**. Non-game PC apps may instead use a secure third-party purchase API and third-party recurring billing; using own commerce keeps **100% of Store revenue before processor/vendor fees**. Unpackaged Store listings use own/third-party commerce rather than Store commerce. [Microsoft subscription add-ons](https://learn.microsoft.com/en-us/windows/uwp/monetize/enable-subscription-add-ons-for-your-app), [StoreContext purchases](https://learn.microsoft.com/en-us/windows/uwp/monetize/in-app-purchases-and-trials), [Store revenue model](https://learn.microsoft.com/en-us/windows/apps/publish/get-started), [Store policies 10.8.1 and 10.8.6](https://learn.microsoft.com/en-us/windows/apps/publish/store-policy-archive/store-policy-7-19), [Win32 Store comparison](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store).

There is no documented RevenueCat **native Microsoft Store purchase SDK** in its platform installation list. RevenueCat does document a **Web SDK** and React Native web support, with RevenueCat Billing/Stripe Billing/Paddle Billing as supported engines and shared entitlements. Thus the Windows shell can open a secure web checkout or use the web UI, then refresh entitlements for the same account; it should not call the macOS App Store RevenueCat purchase path on Windows. [RevenueCat SDK platforms](https://www.revenuecat.com/docs), [RevenueCat Web integrations](https://www.revenuecat.com/docs/web/payment-integrations), [React Native web support](https://www.revenuecat.com/docs/getting-started/installation/reactnative).

Direct alternatives are **Stripe Billing/Checkout**, **Paddle Billing** (merchant of record), or **Lemon Squeezy** (subscription plus license-key API). These are web/payment services usable by a Windows app, not Windows-native purchase APIs. Paddle documents signed webhooks and subscription-state provisioning; Lemon Squeezy documents license activation/validation and subscription-expiry behavior. Keep payment API secrets and webhook verification on the backend. Map provider customer/subscription IDs to the user's Account, update entitlement on verified webhook events, and have the desktop app query a backend entitlement with a stated offline grace policy. A local-only flag cannot be authoritative for a paid subscription. [RevenueCat billing engines](https://www.revenuecat.com/docs/web/payment-integrations), [Paddle provisioning](https://developer.paddle.com/build/subscriptions/provision-access-webhooks/), [Paddle signature verification](https://developer.paddle.com/webhooks/about/signature-verification/), [Lemon Squeezy license API](https://docs.lemonsqueezy.com/api/license-api), [Lemon Squeezy webhooks](https://docs.lemonsqueezy.com/help/webhooks).

## Cross-platform carry-over and ranked risks

The Expo web React screens, TypeScript domain/client code, Convex API calls, protocol types, and much of Electron shell logic are plausible shared code. Expo explicitly supports exporting a web bundle; Electron runs web content. Windows-specific work includes replacing Swift capture/host integration, installer/signing/update pipelines, native window/tray conventions, platform path/process discovery, and Windows billing entry points. The amount of code reuse is therefore **high for UI and shared services but low for capture and distribution**; a percentage would be speculative without a dependency audit. [Expo web export](https://docs.expo.dev/deploy/web/), [Electron application packaging](https://www.electronjs.org/docs/latest/tutorial/application-distribution), [Windows WASAPI](https://learn.microsoft.com/en-us/windows/win32/coreaudio/wasapi), [Win32 Store comparison](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store).

1. **Audio capture quality and privacy:** simultaneous mic/system capture, device switches, protected streams, and recording disclosure need a Windows prototype. WASAPI loopback is available but not identical to the Swift host. [WASAPI loopback](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [Store privacy rules](https://learn.microsoft.com/en-us/windows/apps/publish/store-policy-archive/store-policy-7-19).
2. **CLI integration across Windows, MSIX, and WSL:** process launching is available, but install location, `PATH`, per-user auth, enterprise policy, and S mode differ. Test the exact Ask invocation and capture stdout/stderr under each distribution channel. [MSIX trust](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview), [Desktop Bridge tests](https://learn.microsoft.com/en-us/windows/uwp/debug-test-perf/windows-desktop-bridge-app-tests), [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop).
3. **Signing and update reliability:** direct distribution brings certificate eligibility, early SmartScreen friction, and update security/rollback responsibilities; Store MSIX removes some of these but adds package testing. [Code-signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options), [electron-updater](https://www.electron.build/docs/features/auto-update/), [Store distribution comparison](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store).
4. **Subscription state across Mac and Windows:** share account identity and entitlement mapping, reconcile cancellations/refunds through provider events, and define offline access. RevenueCat supports web and native entitlements under one user ID, while Microsoft Store purchases would require an additional Store integration. [RevenueCat Web](https://www.revenuecat.com/docs/web/payment-integrations), [Microsoft StoreContext](https://learn.microsoft.com/en-us/windows/uwp/monetize/in-app-purchases-and-trials).

**Next proof:** build one signed Electron Windows prototype with WASAPI mic+loopback capture, tray recording, and `codex`/`claude` discovery under a normal user; test it as NSIS and then as MSIX with the certification kit before choosing whether to publish the MSIX channel. The APIs and packaging paths above support that test; its results will determine whether Store MSIX can preserve the Ask feature reliably. [WASAPI](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [Electron native addons](https://www.electronjs.org/docs/latest/tutorial/native-code-and-electron), [Windows App Certification Kit](https://learn.microsoft.com/en-us/windows/uwp/debug-test-perf/windows-app-certification-kit).
