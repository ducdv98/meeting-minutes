# Windows audio capture feasibility for Meeting Minutes

Research date: 2026-10-12. Scope: local recording of the user's microphone and meeting playback as separately identifiable sources, recoverable during a crash, with a locally finalized MP3. This is a technical feasibility assessment, not a claim that every headset, driver, or conferencing app has been tested.

## Verdict and recommendation

**Feasible on Windows 11 and recent Windows 10 builds.** A shared-mode WASAPI capture client can read an output endpoint's system mix, while another client records a microphone. Windows also offers process-loopback activation that includes or excludes a target PID and its child processes, independent of the output endpoint. The latter is useful for Zoom or Teams desktop processes but cannot reliably mean “one browser tab.” Microsoft documents the process-loopback enum and sample as requiring Windows 10 build **20348** or later; one `ActivateAudioInterfaceAsync` page says **20438** instead, so feature-detect and validate on the actual minimum supported builds. [Microsoft loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [Microsoft application-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [process-loopback enum](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode), [activation API](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync).

**Recommended stack:** a small native Windows capture component using the [Rust `wasapi` crate](https://docs.rs/wasapi/latest/wasapi/) (which has loopback, process-loopback, device notifications, and a `record_application` example), with direct Windows bindings where packet timestamps, permission diagnostics, or recovery need them. Keep UI/transcription separate from the real-time capture threads. Start with endpoint loopback plus microphone for robust call coverage; offer process-tree capture as an opt-in way to exclude unrelated computer audio. Keep original source chunks and a timestamped manifest, then create a listening/transcription mix and encode the final MP3 locally with the Windows [Media Foundation MP3 encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/mp3-audio-encoder). This architecture is a recommendation derived from the APIs and failure modes below.

## 1. System output and application output

| Mode | What it captures | Limit / implication |
| --- | --- | --- |
| Endpoint loopback | Shared-mode audio rendered to one chosen output endpoint, including other apps on that endpoint. Initialize an `IAudioClient` on a **render** endpoint with `AUDCLNT_STREAMFLAGS_LOOPBACK`, then read `IAudioCaptureClient`. | A Bluetooth/headset/default-device switch can move playback away from the captured endpoint. Monitor default-device and disconnection events and reopen; there can be a gap. [Microsoft loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [device events](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-events), [invalid-device recovery](https://learn.microsoft.com/en-us/windows/win32/coreaudio/recovering-from-an-invalid-device-error). |
| Process loopback | Render streams from one PID **and descendants**, or everything except that tree, using `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`, `AUDIOCLIENT_ACTIVATION_PARAMS`, and `ActivateAudioInterfaceAsync`. | Not tied to a physical endpoint, so it is less sensitive to output-device switches. Targeting is by process tree, not window, application name, audio session, or web tab. Reacquire when a meeting app restarts or changes process ownership. [Microsoft sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [process-loopback mode](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode), [OBS implementation](https://github.com/obsproject/obs-studio/blob/master/plugins/win-wasapi/win-wasapi.cpp). |

For `Zoom.exe` or Teams, identify the *actual process rendering the call audio* and test whether its children cover the stream. The API does not promise that selecting a process merely because its window belongs to the meeting will capture all its audio; OBS finds a window's PID and activates process loopback, illustrating both the approach and its dependency on correct PID selection. For browser meetings, Chromium may share renderer processes among related pages and uses a separate audio-service utility process; a tab is therefore not a stable WASAPI process-tree boundary. Treat browser process capture as potentially including unrelated tabs or missing audio; endpoint loopback is the reliable fallback. [Microsoft process-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [OBS source](https://github.com/obsproject/obs-studio/blob/master/plugins/win-wasapi/win-wasapi.cpp), [Chromium site-isolation design](https://www.chromium.org/developers/design-documents/site-isolation/), [Chromium Windows process diagnostics](https://www.chromium.org/Home/chromium-security/articles/chrome-sandbox-diagnostics-for-windows/). This browser conclusion is an inference from process-scoped WASAPI and Chromium's process model, not a Microsoft guarantee about a particular browser release.

Endpoint loopback works only in **shared** mode. It does not capture protected DRM content; exclusive-mode playback may preempt shared streams. Windows 10 version 1703 and newer supports event-driven endpoint loopback directly; older versions need the documented render-event workaround. A quiet endpoint may deliver no packets rather than continuous zero samples; the process-loopback sample says a non-rendering target yields silence, and NAudio documents no `DataAvailable` event during quiet periods. The recorder must advance its own timeline and insert explicit silence instead of treating missing callbacks as a paused meeting. [Microsoft loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [Microsoft exclusive-mode streams](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams), [Microsoft process-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [NAudio loopback documentation](https://github.com/naudio/NAudio/blob/main/Docs/WasapiLoopbackCapture.md).

Negotiate each endpoint's actual mix format with `GetMixFormat`/`IsFormatSupported`; Windows' audio engine does not promise arbitrary shared-mode sample-rate or channel conversion. Convert each source to an internal common format only after capture. A communications Bluetooth device can expose different rates and mono/stereo behavior while its microphone is active, so test headsets explicitly. [Microsoft device formats](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-formats), [Microsoft communications format guidance](https://learn.microsoft.com/en-us/windows/win32/coreaudio/communications-audio-format-capabilities).

## 2. Concurrent microphone capture and alignment

Open a second shared-mode `IAudioClient` on the desired **capture** endpoint, drain its `IAudioCaptureClient` independently of loopback, and retain separate mic/system recordings. `GetBuffer` exposes frame count, device position, QPC time for the first frame, and silent/discontinuity/timestamp-error flags; these are useful for a common timeline and diagnostics. Mic and render hardware have independent clocks, so equal nominal rates do not guarantee equal real-time sample counts. [Microsoft capturing a stream](https://learn.microsoft.com/en-us/windows/win32/coreaudio/capturing-a-stream), [`IAudioCaptureClient::GetBuffer`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer), [NAudio mixing guide](https://github.com/naudio/NAudio/blob/main/Docs/MixMicrophoneAndSystemAudio.md).

Recommended pipeline: timestamp packets against one monotonic timeline; write each source's native-format chunks and start time; convert to 48 kHz float for a **derived** mix; use a bounded jitter buffer, pad gaps with silence, and estimate long-run clock-rate error to apply small adaptive resampling corrections. Keep source gain/headroom controls before summing, since two full-scale sources can clip. NAudio's current mixing guide demonstrates normalization and wall-clock-paced mixing, explains drift and silent loopback gaps, and warns that some drivers provide inconsistent QPC positions. Therefore validate QPC behavior per device and fall back to arrival-time pacing when timestamps are bad; neither method gives sample-perfect alignment without measurement. [NAudio mixing guide](https://github.com/naudio/NAudio/blob/main/Docs/MixMicrophoneAndSystemAudio.md), [`GetBuffer` flags and timestamps](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer).

## 3. Acoustic echo and source separation

With speakers, remote audio comes out of the speakers **and** leaks acoustically into the local microphone. Simply adding mic and loopback can make remote voices louder, delayed, or doubled; keeping tracks separate allows later gain, muting, or echo processing, but does not remove leaked voice from the raw mic track. A headset reduces this acoustic path. Windows describes AEC as using both microphone input and a render reference; supported capture endpoints may expose `IAcousticEchoCancellationControl`, but availability and quality depend on the endpoint/driver, and the conferencing app's own AEC does not automatically process the app's independent Microphone capture. Treat software AEC as a measured enhancement, not a baseline requirement. [Microsoft AEC APO architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/windows-11-apis-for-audio-processing-objects), [WASAPI interfaces](https://learn.microsoft.com/en-us/windows/win32/coreaudio/wasapi).

## 4. Permissions and failure diagnosis

For an unpackaged desktop app, Windows exposes device-level microphone access and an “Allow desktop apps to access your microphone” switch; desktop apps do not get individual privacy toggles. A packaged MSIX app with package identity should declare its microphone device capability, and AppContainer packaging has additional capability constraints. For packaged apps, `AppCapability` can report `Allowed`, `DeniedByUser`, `DeniedBySystem`, `NotDeclaredByApp`, or `UserPromptRequired`. At startup, show a live mic meter and handle capture activation/initialization failures; distinguish permission denial from no device, muted device, or silence rather than inferring access from an empty buffer alone. [Microsoft microphone settings](https://support.microsoft.com/en-us/windows/privacy/turn-on-app-permissions-for-your-microphone-in-windows), [Microsoft camera/microphone privacy details](https://support.microsoft.com/en-us/windows/privacy/windows-camera-microphone-and-privacy), [capability declarations](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations), [capability status enum](https://learn.microsoft.com/en-us/uwp/api/windows.security.authorization.appcapabilityaccess.appcapabilityaccessstatus).

The cited Microsoft WASAPI loopback and process-loopback procedures specify no separate loopback-consent dialog or microphone capability for **render** capture. That is a documentation-based inference, not a promise that no enterprise policy, application sandbox, or future Windows privacy change can block it. Probe activation and verify non-silent samples during a known test tone. [Microsoft loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [Microsoft process-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/).

## 5. Implementation options and precedents

| Option | Assessment |
| --- | --- |
| Rust `wasapi` | Strongest fit for a small native helper: its documented APIs include endpoint loopback, process-specific loopback, recording, and device notifications. Inspect/extend bindings for precise packet handling and recovery. **Caveat:** the `new_application_loopback_client` documentation says `include_tree = false` captures only the target, but its source maps `false` to `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`, which captures everything *except* that tree. Use `true` for target-process recording and test this behavior explicitly. [crate docs](https://docs.rs/wasapi/latest/wasapi/), [`AudioClient` source](https://docs.rs/wasapi/latest/src/wasapi/api.rs.html#787-800), [Microsoft mode definitions](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode). |
| Rust `cpal` | Mature cross-platform basic input/output with WASAPI backend, but its abstraction is less direct for process targeting and Windows-specific recovery. Its WASAPI backend has loopback support; verify needed behavior on current releases. [CPAL README](https://github.com/RustAudio/cpal), [WASAPI source](https://github.com/RustAudio/cpal/blob/master/src/host/wasapi/mod.rs). |
| C++/WinRT or Win32 helper | Most direct match to Microsoft's maintained C++ `ActivateAudioInterfaceAsync` sample and OBS's production C++ process-loopback implementation, with more COM/real-time code to maintain. [Microsoft sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [OBS source](https://github.com/obsproject/obs-studio/blob/master/plugins/win-wasapi/win-wasapi.cpp). |
| .NET NAudio | Fastest Windows prototype: NAudio 3 documents `WasapiRecorder` for mic, endpoint loopback, and `WithProcessLoopback` plus a two-source mixer. Its docs claim process loopback works from build 19041, conflicting with Microsoft's 20348 enum/sample requirement; validate rather than adopting that lower floor. [NAudio recorder](https://github.com/naudio/NAudio/blob/main/Docs/WasapiRecorder.md), [mixing guide](https://github.com/naudio/NAudio/blob/main/Docs/MixMicrophoneAndSystemAudio.md), [Microsoft enum](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode). |
| Node/Electron | Electron `desktopCapturer` documents `audio: 'loopback'` in display-media handling; that is a route to system audio but not a documented PID-filtered, crash-safe two-source recorder. `naudiodon` wraps PortAudio for device I/O; its README does not promise process loopback. Prefer native capture below the JS UI for precise timestamps, reconnects, and durable chunks. [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer), [naudiodon README](https://github.com/Streampunk/naudiodon). |

Existing open-source evidence: OBS uses native WASAPI for endpoint input/output and `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK` for application audio; Meetily's Windows release notes report optimized WASAPI capture; Screenpipe uses a CPAL fork with WASAPI on Windows, and its Windows integration test checks actual captured RMS because a near-silence regression could otherwise look healthy. These establish precedent but do not prove the app's own reliability. [OBS source](https://github.com/obsproject/obs-studio/blob/master/plugins/win-wasapi/win-wasapi.cpp), [Meetily releases](https://github.com/Zackriya-Solutions/meetily/releases), [Screenpipe CPAL fork](https://github.com/screenpipe/cpal), [Screenpipe Windows test](https://github.com/screenpipe/screenpipe/blob/main/.github/workflows/windows-integration-test.yml).

## 6. Encoding and crash-safe recording

Windows Media Foundation includes an MP3 encoder on Windows 8 and later desktop systems. Its input is **16-bit integer PCM**, not float, and input rate/channel count must match a supported output type; ordinary MPEG-1 modes include mono/stereo at 32, 44.1, or 48 kHz. Convert the finalized mix accordingly and test actual encoder availability at startup. LAME is an alternate bundled encoder under LGPL terms, which adds license-distribution obligations; Opus has a BSD-licensed reference implementation and royalty-free patent grant, useful for compact intermediate chunks but not a substitute for the requested final MP3. [Microsoft MP3 encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/mp3-audio-encoder), [LAME project](https://github.com/lameproject/lame), [Opus licensing](https://opus-codec.org/license/).

**Proposed durability protocol (engineering recommendation):** write short, independently readable per-source PCM/WAV or Opus chunks; give each chunk a source, start time, frame count, format, and sequence number in a manifest; close and flush each chunk before marking it complete; on restart, ignore/truncate only the final incomplete chunk and rebuild the derived mix. This avoids making a single long MP3 or WAV header the only copy of the meeting. Finalize one MP3 to a temporary path only after both source timelines are reconciled, then publish it after successful close/flush. Windows provides `FlushFileBuffers` for flushing file data and `MoveFileEx` for rename/replacement; exact power-loss guarantees still depend on filesystem and hardware. [Microsoft `FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), [Microsoft `MoveFileEx`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [Microsoft MP3 encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/mp3-audio-encoder).

## Ranked risks and validation gates

1. **Wrong or missing meeting audio.** Process ownership is especially ambiguous for browsers; endpoint routing can change mid-call; silence can mean quiet, wrong endpoint, or broken capture. Gate: Zoom, new Teams, Chrome/Edge Meet, wired headset, Bluetooth headset, speakers; verify separate track RMS and injected test tones, including process restart and device switch. [Microsoft process-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [Chromium process model](https://www.chromium.org/developers/design-documents/site-isolation/), [device events](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-events), [Screenpipe Windows test](https://github.com/screenpipe/screenpipe/blob/main/.github/workflows/windows-integration-test.yml).
2. **Audio gaps or drift in long recordings.** Independent clocks, no-callback silence, discontinuities, and device invalidation can corrupt timing. Gate: one-hour calls with scripted silence and device changes; compare elapsed time to each source's sample count and inspect discontinuity markers. [Microsoft capture packet metadata](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer), [NAudio mixing guide](https://github.com/naudio/NAudio/blob/main/Docs/MixMicrophoneAndSystemAudio.md), [invalid-device recovery](https://learn.microsoft.com/en-us/windows/win32/coreaudio/recovering-from-an-invalid-device-error).
3. **Speaker echo and duplicated speech.** Gate: speakers and headset recordings, with mic/system tracks listened to separately and as a mix; set conservative mix gains and evaluate AEC only with an appropriate render reference. [Microsoft AEC architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/windows-11-apis-for-audio-processing-objects), [NAudio mixing guide](https://github.com/naudio/NAudio/blob/main/Docs/MixMicrophoneAndSystemAudio.md).
4. **Mic privacy/packaging failures.** Gate: desktop privacy off, device missing, disabled mic, and any MSIX/AppContainer package; show specific failure and retain system capture if mic fails. [Microsoft microphone settings](https://support.microsoft.com/en-us/windows/privacy/turn-on-app-permissions-for-your-microphone-in-windows), [capability declarations](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations).
5. **Crash recovery and final encode.** Gate: kill the process during capture, chunk rollover, and MP3 finalization; recover playable source chunks and regenerate a final MP3. [Microsoft MP3 encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/mp3-audio-encoder), [`FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

The principal unresolved empirical questions are which PID actually renders audio in each supported meeting-app version, how specific Bluetooth drivers behave on mode/device changes, and whether the chosen minimum Windows build activates process loopback in practice. The API documentation and open-source precedents support feasibility; the gates above determine product reliability. [Microsoft process-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [Microsoft communications-device guidance](https://learn.microsoft.com/en-us/windows/win32/coreaudio/communications-audio-format-capabilities), [Microsoft enum and activation API](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode), [activation API](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync).
